# IP development guide 🧩


> 🧰 **Shell setup used in this guide**
>
> Install/sync dependencies once, then activate the project environment:
>
> ```bash
> uv sync
> source .venv/bin/activate
> ```
>
> After activation, run commands directly with `fx ...`.

This guide walks through a complete single-clock IP development flow. The example
IP is called `stream_accel`, but the same sequence works for any small IP.

## 0. Start from a clean run

```bash
fx settings TOP=stream_accel RUN_TOP=stream_accel RUN_ID=dev HOST=uart
fx setup
```

The workspace is created at:

```text
workspace/runs/stream_accel/dev
```

## 1. Generate the register-map source

```bash
fx hjson --force
```

This creates:

```text
data/stream_accel.hjson
```

Open it and describe the software-visible interface. A useful IP usually needs a
few control, configuration, status and result registers. For example:

- `CTRL`: enable, start and clear bits.
- `MODE`: algorithm selector and options.
- `OPERAND_A`, `OPERAND_B`, `SCALE`: runtime parameters.
- `STATUS`: busy, done and error flags.
- `RESULT`: hardware-produced result.

Keep the HJSON readable. Avoid adding registers until the RTL needs them.

## 2. Generate register RTL and documentation

```bash
fx reg doc --force
```

This creates the register package/top and Markdown documentation:

```text
rtl/stream_accel_reg_pkg.sv
rtl/stream_accel_reg_top.sv
doc/stream_accel.md
```

### Regmap access rule

The register package defines the exact `reg2hw` and `hw2reg` structure. Use that
structure in the core.

Single-field registers are flat:

```systemverilog
// Single-field register generated by reggen.
logic [31:0] operand_a;
assign operand_a = reg2hw_i.operand_a.q;

// Hardware-owned single-field register.
assign hw2reg_o.result.d = result_q;
```

Multi-field registers are nested:

```systemverilog
// Multi-field register generated by reggen.
logic ctrl_en;
logic ctrl_clr;
assign ctrl_en  = reg2hw_i.ctrl.en.q;
assign ctrl_clr = reg2hw_i.ctrl.clr.q;

// Hardware-owned multi-field status register.
assign hw2reg_o.status.busy.d  = busy_q;
assign hw2reg_o.status.done.d  = done_q;
assign hw2reg_o.status.error.d = error_q;
```

## 3. Generate the RTL stub

```bash
fx rtl_stub --force
```

This creates:

```text
rtl/stream_accel.sv
rtl/stream_accel_core.sv
```

Edit `stream_accel_core.sv`. Keep reset and clear semantics clean:

```systemverilog
// Reset is asynchronous because it is in the event list.
always_ff @(posedge clk_i or negedge rst_ni) begin
  if (!rst_ni) begin
    result_q <= '0;
    valid_q  <= 1'b0;
  end else if (ctrl_clr) begin
    // Software clear is synchronous, so it stays under the clocked branch.
    result_q <= '0;
    valid_q  <= 1'b0;
  end else begin
    // Normal datapath update.
    result_q <= next_result;
    valid_q  <= valid_i;
  end
end
```

## 4. Regenerate the top wrapper from the core

If you edit the core interface, regenerate the top wrapper:

```bash
fx top_from_core --force
```

This keeps `stream_accel.sv` aligned with `stream_accel_core.sv`.

## 6. Generate the editable model

```bash
fx setup_model --force
```

This creates the editable reference model:

```text
model/model_stream_accel.py
```

Generate vector tests explicitly from that model:

```bash
fx tests_gen
fx test_gen --set TEST_NAME=my_new_case
```

The generated model is the source of verification tests. It writes:

```text
tb/tests/<test>/config.regs
tb/tests/<test>/data_in.vec
tb/tests/<test>/data_out.vec
```

### How to add a new test

Open `model/model_stream_accel.py`. You will see a `TESTS` list and small helper
functions.

Add a new test entry:

```python
TESTS = [
    {"name": "smoke", "mode": 0, "samples": [(3, 1), (4, 2)]},
    {"name": "saturation", "mode": 2, "samples": [(0xFFFF, 8), (0x1000, 4)]},
]
```

Then implement or adjust the model function:

```python
def expected(sample: tuple[int, int], mode: int) -> int:
    '''Return the expected DUT output for one input sample.'''

    data, coeff = sample
    if mode == 0:
        return data + coeff
    if mode == 1:
        return data ^ coeff
    return min(data * coeff, 0xFFFFFFFF)
```

Generate vectors from the edited model:

```bash
fx setup_model
```

Use `--force` only when you want to replace the model template itself. Without
`--force`, the model is preserved and the vector files are regenerated.

## 7. Understand the generated verification files

### `config.regs`

Register writes, one per line:

```text
clk_i.CTRL 0x00000003
clk_i.MODE 0x00000000
clk_i.OPERAND_A 0x00000001
```

The old `write` keyword is optional and no longer needed.

### `data_in.vec`

Input stimulus. Use one signal/value pair per row. Repeat the same cycle to drive
multiple signals together:

```text
0 data_i 0x00000003
0 coeff_i 0x00000001
0 valid_i 0x00000001
```

### `data_out.vec`

Expected output values:

```text
1 data_o 0x00000004
1 valid_o 0x00000001
```

### Runtime reconfiguration

Change register configuration during simulation with `@cfg`:

```text
4 @cfg /absolute/path/to/config_xor.regs
```

The testbench applies the new config at that vector cycle and continues.

## 8. Generate SV and cocotb testbench scaffolds

```bash
fx setup_tb --force
fx setup_cocotb --force
```

These targets create only verification infrastructure: drivers, monitors, and
testbench files. They do not generate `config.regs`, `data_in.vec`, or
`data_out.vec`; those files always come from `tests_gen` / `test_gen`.

Both flows consume the same vector files. The model is not imported by the
simulator after the vectors are generated.

List tests:

```bash
fx tests
```

Run one test by name:

```bash
fx sim --set TEST_NAME=smoke
fx cocotb --set TEST_NAME=smoke
```

Run the full IP regression:

```bash
fx sim_tests
fx cocotb_tests
```

## 9. Synthesis, SDF, STA and power

```bash
fx syn --force
fx sdf
fx sta
fx power
```

`sta`, `sdf` and `power` are explicit steps. They do not rerun synthesis for you.
This makes it clear which netlist and constraints are being analyzed.

## 10. Recommended iteration loop

During development, use this loop:

```bash
fx reg doc rtl_stub flist lint --force
fx setup_model tests_gen setup_tb setup_cocotb
fx sim --set TEST_NAME=smoke
fx cocotb --set TEST_NAME=smoke
```

When stable, run the full flow:

```bash
fx lint sim_tests cocotb_tests syn sdf sta power --force
```

## Signoff reports

After synthesis, run:

```bash
fx sdf sta power --force
```

`fx sta` expands to setup and hold analysis for every corner in `SIGNOFF_CORNERS`. `fx power` expands to power analysis for the same corners. Detailed signoff logs are written under `logs/signoff/`. No extra summary report is generated by default.

Verification logs are also test-name aware:

```bash
logs/verification/<top>_sv_sim_<TEST_NAME>.log
logs/verification/<top>_cocotb_<TEST_NAME>.log
```
