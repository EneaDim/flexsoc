# Single-clock IP development guide

This guide covers an IP whose initial RTL/model scaffold is generated by
FlexSoC. For an already implemented IP under `hw/ips/`, use
[Existing IP development](guide_existing_ip_dev.md).

## 1. Configure the run

```bash
fx settings TOP=test RUN_TOP=test RUN_ID=dev HOST=uart CLOCK_MODE=single
```

`TOP` is the module instantiated by the generated verification infrastructure.

## 2. Create the run and register map

```bash
fx setup --force
fx hjson --force
```

Edit:

```text
workspace/runs/test/dev/data/test.hjson
```

Generate register RTL and documentation:

```bash
fx reg doc --force
```

The HJSON file is the source of truth for software-visible register structure.

## 3. Create and edit the RTL

```bash
fx rtl_stub --force
```

The generated run contains the editable core and top wrapper under `rtl/`.
Edit the core implementation. If the core port list changes and the wrapper is
still generated collateral, refresh it with:

```bash
fx top_from_core --force
```

Do not use `top_from_core` when the top wrapper has become a deliberately custom
source file; that case follows the existing-IP ownership rules.

## 4. Generate filelists and lint

```bash
fx flist --force
fx lint
```

Focused diagnostics:

```bash
fx lint_latch
fx lint_width
fx lint_unconnected
fx lint_undriven
fx lint_unused
```

Detailed logs are written under `logs/lint/`.

## 5. Bootstrap the model once

```bash
fx setup_model --force
```

This creates:

```text
model/model_test.py
model/regmap_test.py
```

Ownership is strict:

- `model_test.py` is editable behavioral code;
- `regmap_test.py` is generated from HJSON and should not be hand-edited.

`setup_model` without `--force` preserves files that already exist.
`setup_model --force` rewrites both files, including the behavioral model, so
use it only when bootstrapping or intentionally resetting the scaffold.

### Updating the HJSON later

After the model has been customized, update only generated register collateral:

```bash
fx reg doc --force
fx regmap_py --force
```

`regmap_py --force` rewrites only `regmap_test.py`; it does not touch
`model_test.py`.

## 6. Use the generated CSR API

A single-clock model imports the generated regmap and selects its primary
register domain:

```python
import regmap_test as regmap

CSR = regmap.PRIMARY
```

Each HJSON register is exposed as a register object. Field values are encoded
from generated metadata:

```python
CSR.CTRL(TX=1, RX=1)
CSR.CTRL.write(TX=1, RX=1)
CSR.CTRL.vector_write(8, TX=1, RX=1)
CSR.STATUS.vector_read(32, BUSY=0, VALID=1)
```

The generated objects own register offsets, field positions, reset values,
access properties, and field masks. Keep those details out of the behavioral
model.

For multiple generated register domains, use:

```python
regmap.domain("domain_name")
```

## 7. Define test scenarios clearly

The default scaffold organizes each scenario into three explicit sections:

```python
@dataclass
class TestCase:
    config: list[str]
    data_in: list[str]
    data_out: list[str]
```

Use them consistently:

- `config`: initial CSR configuration;
- `data_in`: direct input drives and/or CSR `@write` operations;
- `data_out`: direct output checks and/or CSR `@read` expectations.

An IP can therefore be:

- port-driven;
- CSR-driven;
- mixed, like UART, where pins carry serial data while CSRs configure and check
  the block.

A CSR-only IP such as CORDIC can keep direct port vectors empty and perform all
stimulus/checks through the register interface.

## 8. Generate vector tests

Generate every scenario listed by the model:

```bash
fx tests_gen --force
```

Generate one scenario:

```bash
fx test_gen --set TEST_NAME=my_case
```

List generated tests:

```bash
fx tests
```

Each test is materialized as:

```text
tb/tests/<TEST_NAME>/
├── config.regs
├── data_in.vec
└── data_out.vec
```

The simulators never import the behavioral model directly; they consume these
files.

### `config.regs`

Initial CSR operations, for example:

```text
clk_i.CTRL 0x00000003
clk_i.FIFO_CTRL 0x00000003
```

### `data_in.vec`

Direct input drive:

```text
32 cio_rx_i 0x00000000
```

CSR write:

```text
8 @write clk_i.WDATA 0x0000005a 0x000000ff
```

### `data_out.vec`

Direct output check:

```text
16 cio_tx_o 0x00000001
```

CSR read/check:

```text
400 @read clk_i.RDATA 0x0000005a 0x000000ff
```

## 9. Generate verification infrastructure

```bash
fx setup_tb --force
fx setup_cocotb --force
```

These commands generate drivers, monitors, wrappers, and simulator glue. They
do not define behavioral scenarios; those remain in the model/vector files.

## 10. Run verification

One test:

```bash
fx sim --set TEST_NAME=smoke
fx cocotb --set TEST_NAME=smoke
```

All generated tests:

```bash
fx sim_tests
fx cocotb_tests
```

Waveforms:

```bash
fx view --set TEST_NAME=smoke
fx view_cocotb --set TEST_NAME=smoke
```

## 11. Synthesis and signoff

```bash
fx syn sdf sta power --force
```

Use `--live` only when full tool output is useful:

```bash
fx syn sdf sta power --force --live
```

## 12. E2E regression

```bash
pytest -s tests/test_e2e_fx.py --no-signoff
```

The E2E suite uses temporary workspaces under `/tmp`, not the repository
`workspace/` tree. Remove `--no-signoff` to include synthesis/signoff.
